**5. Build tenant isolation as a complete subsystem**

Proposed requirements:

- Every tenant resource has immutable ownership.
- Every tenant database operation executes through a tenant-aware transaction.
- Staff identity, customer identity, and system job identity are distinct.
- Membership is verified before selecting an organization.
- A browser may request an organization switch; the server validates it.
- Database access uses restricted runtime roles.
- Migration credentials are separate from application credentials.
- Tenant context is set transaction-locally on the same connection used for queries.
- Context is absent by default and fails closed.
- Related tenant records use composite foreign keys.
- Sensitive columns are excluded from public responses.
- Support access uses a dedicated audited authorization path.

The transaction wrapper should conceptually perform:

```text
Authenticate actor
→ Resolve requested organization
→ Verify active membership or customer scope
→ Authorize operation
→ Begin database transaction
→ Establish transaction-local context
→ Execute tenant-scoped queries
→ Write audit/outbox records where necessary
→ Commit
```

Treat the database session variable as **trusted backend context**, not as an independent cryptographic identity mechanism. Do not expose an API that lets clients arbitrarily set it.

For composite ownership:

```text
orders:
  UNIQUE (organization_id, id)

order_items:
  FOREIGN KEY (organization_id, order_id)
  REFERENCES orders (organization_id, id)
```

Apply the same ownership approach to product variants, refunds, customer addresses, booking resources, and attachments.

The isolation test matrix must include:

| Boundary | Required negative test |
|---|---|
| Database | Tenant A cannot read or mutate Tenant B’s private records |
| Foreign keys | A cannot attach a B resource to an A record |
| API | Guessed IDs do not bypass ownership |
| Cache | A’s cached output never appears under B’s host |
| Search | Private search cannot return another tenant’s results |
| Storage | A cannot upload to or download B’s private objects |
| Realtime | A cannot subscribe to B’s operational events |
| Jobs | Altered job metadata cannot redirect work into B |
| AI | Tools cannot act on another organization |
| Support | Tenant users cannot reach platform support capabilities |

Test with the actual runtime database roles and connection pooling configuration. PostgreSQL’s default-deny behavior and bypass rules must be accounted for in that test setup. ([postgresql.org](https://www.postgresql.org/docs/current/ddl-rowsecurity.html?utm_source=openai))

**11. Engineer checkout as a recoverable transaction workflow**

Proposed sequence:

```text
Resolve site and customer/cart scope
→ Check current transaction entitlement
→ Validate cart
→ Calculate authoritative prices, discounts, tax, and delivery
→ Create checkout/order snapshot
→ Reserve stock or capacity
→ Persist payment creation operation
→ Request provider payment session
→ Store provider reference
→ Customer pays
→ Verified webhook records payment outcome
→ Worker confirms order and consumes reservation
→ Outbox triggers fulfillment notifications
```

Do not hold a database transaction open during a payment-provider network call.

Persist the operation before calling the provider. If the request times out, use the same provider idempotency key and reconcile the existing operation.

Separate states:

| Aggregate | Proposed states |
|---|---|
| Order | draft, submitted, accepted, canceled, completed |
| Payment | pending, requires_action, authorized, captured, failed |
| Fulfillment | unfulfilled, partial, ready, shipped, delivered |
| Refund | requested, processing, succeeded, failed |
| Return | requested, approved, received, rejected |
| Dispute | open, evidence_submitted, won, lost |

Required edge cases:

- Double-clicked checkout.
- Identical retries.
- Same idempotency key with different payload.
- Provider timeout after successful creation.
- Payment success after reservation expiry.
- Merchant rejection after payment.
- Partial fulfillment.
- Partial refund.
- Concurrent refunds.
- Discount quota contention.
- Tax quote expiration.
- Asynchronous payment methods.
- Subscription restriction during an in-progress checkout.

For money, use integer minor units and explicit currency metadata. Define rounding and proportional allocation rules. Serialize large integer amounts safely—for example as decimal strings in API contracts.

**19. Implement recovery, export, and deletion as first-class workflows**

Recovery must cover more than PostgreSQL:

- Database point-in-time recovery.
- Object storage and versions.
- Infrastructure configuration.
- Secrets and key access.
- Active releases.
- Domain mappings.
- Queue reconstruction.
- Search rebuilding.
- External provider reconciliation.
- Previously completed financial operations.
- Deleted-data suppression after restoring old backups.

A restore must not cause a second refund, receipt, or shipment.

Exports should contain a versioned manifest, stable identifiers, relationships, documented formats, and media checksums. Generate exports from a consistent snapshot or documented watermark.

Deletion should:

```text
Authenticate and confirm request
→ Freeze new activity
→ Check operational obligations and retention rules
→ Disable access and integrations
→ Mark deletion generation
→ Cancel/neutralize pending work
→ Delete or anonymize eligible records
→ Delete private files and derived indexes
→ Remove domain mappings
→ Record completion
→ Prevent stale jobs or restored backups from recreating deleted data
```

Use specific retention schedules for raw uploads, AI prompts, messages, webhook payloads, exports, audit records, and financial records. The legal requirements need to be resolved for the actual operating regions and payment model; a CSV export button alone is not evidence of legal compliance.
