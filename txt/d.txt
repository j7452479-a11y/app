1. Product Definition 

Build the platform as a multi-tenant commerce operating system, not merely a website generator. 

Each tenant receives: 

A public storefront. 

A private operations dashboard. 

A configurable business data model. 

A branded subdomain. 

Optional custom-domain support. 

Catalog, ordering, customer, inventory, payments, analytics, and automation tools. 

AI assistance constrained by tenant-level configuration and approved modules. 

A 30-day trial followed by recurring management billing. 

The core product principle should be: 

Users should be able to run their daily business without needing to understand the underlying platform. 

Avoid presenting users with technical concepts such as JSON, schemas, deployments, prompts, tenants, or generated code. Those belong in the platform-admin layer.

3. Critical Product Decisions 

3.1 Do Not Start With Arbitrary AI-Generated Code 

The proposed “vibe coding” layer should not initially generate unrestricted production code. 

Instead, use this hierarchy: 

Natural-language request 

        ↓ 

Intent classification 

        ↓ 

Structured feature configuration 

        ↓ 

Approved component/module 

        ↓ 

Preview environment 

        ↓ 

Automated tests 

        ↓ 

Tenant release 

Example: 

{ 

  "feature": "booking", 

  "enabled": true, 

  "appointment_duration_minutes": 45, 

  "buffer_minutes": 15, 

  "require_deposit": true, 

  "deposit_minor_units": 2000, 

  "currency": "USD" 

} 

This is safer, easier to test, easier to roll back, and more scalable than allowing generated code to modify the core runtime. 

Arbitrary custom code can become a later enterprise feature with: 

Sandboxed execution. 

Strict API permissions. 

CPU and memory limits. 

Network egress restrictions. 

Dependency scanning. 

Human approval. 

Versioned releases. 

Automatic rollback. 

3.2 Make the Dashboard Role-Aware 

Do not show every feature to every user. 

Recommended roles: 

Owner 

Administrator 

Manager

Fulfillment Staff 

Inventory Staff 

Finance Staff 

Marketing Staff

Each role should receive a focused navigation menu. 

For example, fulfillment staff should not see billing settings or staff permissions. 

3.3 Treat Trial Conversion as a Billing State Machine 

Do not implement Day 31 as a single scheduled job. 

Use explicit states: 

trialing 

trial_expiring 

payment_required 

active 

past_due 

grace_period 

restricted 

canceled 

suspended 

closed 

Every billing transition should be driven by verified payment-provider webhooks and recorded in an immutable billing event log. 

Stripe supports trial subscriptions and trial-ending behavior through its billing system, but the platform should still maintain its own synchronized subscription state. (docs.stripe.com)

6.6 Example Organization Schema 

create table organizations ( 

  id uuid primary key default gen_random_uuid(), 

  name text not null, 

  slug text not null unique, 

  business_type text not null, 

  status text not null default 'onboarding', 

  created_at timestamptz not null default now(), 

  updated_at timestamptz not null default now() 

); 

Every tenant-owned table should include: 

organization_id uuid not null references organizations(id) 

Use composite indexes: 

create index orders_organization_created_idx 

on orders (organization_id, created_at desc); 

 

create index products_organization_status_idx 

on products (organization_id, status); 

6.7 Row-Level Security 

Enable RLS on every exposed tenant table. PostgreSQL uses a default-deny behavior when RLS is enabled without an applicable policy, but table grants and policies must still be designed together. (postgresql.org) 

Conceptual policy: 

create policy "members can read organization orders" 

on orders 

for select 

to authenticated 

using ( 

  organization_id in ( 

    select organization_id 

    from organization_members 

    where user_id = auth.uid() 

      and status = 'active' 

  ) 

); 

For writes, use both: 

using (...) 

with check (...); 

Important controls: 

Never permit clients to update organization_id. 

Restrict column updates where necessary. 

Keep service-role access exclusively server-side. 

Add negative cross-tenant tests for every table. 

Test storage paths separately from table policies. 

Test Realtime subscriptions separately from table queries. 

Prevent support impersonation from bypassing audit logging. 

Supabase documentation specifically recommends enabling RLS on every exposed table, defining policies per operation, and adding automated allow/deny tests. (supabase.com)

₹499.00 -> 49900

11.3 Idempotency 

Use idempotency keys for: 

Checkout creation. 

Payment confirmation. 

Order creation. 

Refunds. 

Subscription changes. 

Webhook processing. 

Email dispatch. 

Example: 

idempotency_key = tenant_id + operation + client_request_id 

11.4 Payment Webhooks 

Webhook handling must: 

Verify the provider signature. 

Store the raw event. 

Reject duplicate event IDs. 

Process asynchronously. 

Apply state transitions transactionally. 

Record processing outcomes. 

Retry failures safely. 

Alert on permanently failed events. 

Do not trust the browser’s payment-success redirect as proof of payment.

12.2 Abuse Prevention 

Use risk signals carefully: 

Payment-method fingerprinting. 

Phone verification. 

Email reputation. 

Device risk signals. 

IP reputation. 

Business identity consistency. 

Duplicate domain detection. 

Rate limits. 

Manual review for suspicious activity. 

Do not rely solely on household, device, or IP matching. Shared offices, families, mobile networks, and agencies create false positives. 

12.3 Cancellation and Data Retention 

Define: 

Trial canceled: 

  Storefront disabled immediately or at trial end 

  Dashboard remains available until trial end 

 

Paid cancellation: 

  Service remains active until period end 

 

Past due: 

  Notifications plus limited grace period 

 

Suspended: 

  Storefront disabled 

  Dashboard becomes read-only 

 

Closed: 

  Data retained for legal period 

  Export available 

  Deletion workflow available 

Provide: 

Full CSV export. 

Media export. 

Order export. 

Customer export. 

Configuration export. 

Deletion request workflow. 

Data retention documentation. 

The product should create convenience-based retention, not obstructive lock-in.
