Multi-Tenant Commerce Operating System (Commerce OS)

Master Technical Specification, Multi-Dimensional Feasibility Analysis, Hardened Runtime Architecture, and 24-Work-Package Execution Protocol.

1. Detailed Project Scope & Boundaries

Commerce OS is an enterprise multi-tenant commerce and business management platform that unifies branded storefronts, merchant operations, catalog distribution, order orchestration, appointment bookings, and omnichannel messaging into a multi-tenant SaaS architecture.

In-Scope Functional Boundaries
Core System
  • Multi-Tenant Shared Runtime: Edge-routed storefronts with sub-80ms TTFB across custom domains and subdomains.
  • Merchant Back-Office Dashboard: Full operational portal with Kanban fulfillment, live catalog management, appointment booking calendar, and unified customer communication inbox.
  • Deterministic State Machines: 14-state order machine and 10-state tenant subscription lifecycle with automated order drain protection.
  • Safe AI Action Control Registry: Audited proposal-execution pipeline enforcing risk classification and human-in-the-loop approvals.
  • Statutory Tax & Privacy Compliance: Dual-layer ledger preserving 8-year statutory invoice records while executing GDPR/DPDP personal data erasure.
Explicitly Out-of-Scope Boundaries
Excluded
  • Custom Code Injection / Raw HTML Execution: Merchants cannot inject raw JavaScript into the shared runtime to prevent cross-tenant XSS attacks.
  • Platform Merchant-of-Record (MoR) Liabilities: Platform never acts as legal Merchant of Record; Stripe Connect Direct Charges insulate platform from customer chargebacks.
  • Arbitrary Database Migration by Merchants: Dynamic schemas are represented via strict, versioned JSON capability contracts.
  • Unchecked AI Database Mutation: AI agents cannot execute destructive or customer-facing operations without mandatory merchant sign-off.

2. Multi-Dimensional Feasibility Analysis

2.1 Technical Feasibility & Scale Architecture

The platform utilizes a single PostgreSQL cluster with Row-Level Security (RLS) and transaction-mode connection pooling (PgBouncer/Supavisor). This architecture scales to 10,000+ active tenants while keeping infrastructure overhead minimal.

Connection Scaling Proof

Raw PostgreSQL connections allocate ~10MB of server memory per backend. 1,000 active tenants running 5 concurrent requests each would require 5,000 connections (50GB+ RAM). By using Supavisor/PgBouncer in transaction pooling mode, 10,000 tenants multiplex over a virtualized pool of 64 real database connections, reducing database memory usage to <1.5GB while executing sub-10ms transactional queries.

4. The 7 Fatal Runtime Blindspots & Vulnerabilities

A rigorous architectural review revealed 7 critical runtime blindspots. If left unpatched, these cause silent cross-tenant data breaches, chargeback liabilities, or runtime deadlocks.

Blindspot 1: Connection Pool Session Leaks in ORM Calls

In PostgreSQL, SET LOCAL app.current_tenant_id is only scoped to an explicit transaction block. If an ORM query executes outside an explicit transaction, SET LOCAL becomes a session-level SET. When PgBouncer reuses that connection for Tenant B, Tenant B inherits Tenant A's tenant ID, causing a silent cross-tenant data breach.

Blindspot 2: Stripe Connect Charge Liability (The Chargeback Trap)

Under Stripe Destination Charges or Separate Transfers, the platform becomes the legal Merchant of Record (MoR). Rogue merchant storefronts expose the platform to end-customer disputes and chargebacks debited directly from the platform's corporate bank account.

Blindspot 3: Cross-Tenant Edge CDN Cache Collisions

Standard edge caches index by URL path (e.g., /products/leather-jacket). In a wildcard domain setup, the same path on two tenants shares the same cache entry unless the key explicitly namespaces tenant ID and hostname.

Blindspot 4: In-Flight Order Lockout During Subscription Failure

Immediate dashboard lockouts on payment failure prevent merchants from fulfilling already-paid orders, printing labels, or issuing refunds, causing customer disputes and merchant churn.

Blindspot 5: WhatsApp Cloud API 24-Hour Messaging Window Deadlock

Meta enforces a 24-hour customer care window. Without timestamp tracking, merchants cannot tell whether free-form messages will silently fail, and the system must fall back to paid Meta Template Messages.

Blindspot 6: GDPR / DPDP Erasure vs. Statutory Tax Retention Conflict

Section 44AA / GST / EU VAT mandate retaining invoices and tax records for 6–8 years. Cascading deletes on user deletion violate statutory tax laws.

Blindspot 7: Multi-Agent Monorepo Context Drift & Hallucination

Feeding 100 tables into one LLM agent exceeds reliable context attention, producing hallucinated types and broken foreign keys across packages.

5. The 5 Production Hardening Patches

5.1 Patch 1: Enforce the Atomic withTenantTx Database Wrapper

Mandate that all application database operations execute inside the atomic withTenantTx wrapper. This guarantees role dropping and transaction-local variable scoping. 

// packages/database/src/tenant-context.ts
import { sql } from 'drizzle-orm';
import { db, DrizzleTransaction } from './client';

export async function withTenantTx<T>(
  tenantId: string,
  callback: (tx: DrizzleTransaction) => Promise<T>
): Promise<T> {
  if (!tenantId || !/^[0-9a-f]{8}-[0-9a-f]{4}-[1-5][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i.test(tenantId)) {
    throw new Error('SECURITY_ALERT: Invalid or missing tenant context UUID.');
  }

  return await db.transaction(async (tx) => {
    await tx.execute(sql`SET LOCAL ROLE app_tenant_user;`);
    await tx.execute(sql`SET LOCAL app.current_tenant_id = ${tenantId};`);
    return await callback(tx);
  });
}

5.2 Patch 2: Stripe Connect Direct Charges Architecture

Storefront payments are created directly on the merchant's connected account, making the merchant the legal Merchant of Record and insulating the platform from disputes. 

// packages/payments/src/direct-charge.ts
export async function createStorefrontPaymentIntent({
  stripe, totalMinorUnits, tenantCurrency, platformFeeMinorUnits,
  merchantConnectedAccountId, orderId, tenantId
}) {
  return await stripe.paymentIntents.create(
    { amount: totalMinorUnits, currency: tenantCurrency,
      application_fee_amount: platformFeeMinorUnits,
      metadata: { orderId, tenantId } },
    { stripeAccount: merchantConnectedAccountId }
  );
}

// apps/storefront/lib/cache-key.ts
export function generateEdgeCacheKey(req: Request, tenantId: string, releaseVersion: number): string {
  const url = new URL(req.url);
  const hostname = req.headers.get('host') || 'unknown';
  return `edge:${tenantId}:${hostname}:v${releaseVersion}:${url.pathname}${url.search}`;
}

5.5 Patch 5: The Dual-Layer Anonymization Ledger

Reconciles privacy laws (GDPR/DPDP) with statutory tax retention by scrubbing PII while retaining immutable financial ledgers with hashed pseudonyms. 

// packages/database/src/anonymization.ts
export async function executeRightToBeForgotten(tenantId, customerId) {
  const pseudonym = `REDACTED_${hash(customerId).slice(0, 8)}_${Date.now()}`;

  await db.transaction(async (tx) => {
    // 1. Scrub PII from identity tables
    await tx.update(customers).set({
      fullName: 'Redacted Customer',
      email: `${pseudonym}@redacted.local`,
      phone: null,
      shippingAddressJson: null,
      billingAddressJson: null,
      isAnonymized: true,
      anonymizedAt: new Date(),
    }).where(eq(customers.id, customerId));

    // 2. Preserve immutable financial ledger records for statutory tax retention (8 years)

    // 3. Append audit record
    await tx.insert(auditLogs).values({
      organizationId: tenantId,
      action: 'CUSTOMER_ANONYMIZED',
      entity: 'customer',
      entityId: customerId,
      metadata: { reason: 'GDPR_RIGHT_TO_BE_FORGOTTEN', pseudonym },
    });
  });
}

6.2 Multi-Agent Orchestration Protocol (Atomic Slices)

To prevent context window collapse, the execution follows an Atomic Slice protocol:

  • Lovable: Generates pure TSX/Tailwind markup with typed mock props.
  • Claude Code: Implements backend logic, schema, and RLS-wrapped withTenantTx queries.
  • Antigravity: Coordinates subagents and runs headless browser E2E test journeys.

6.3 Production Release Evidence Register

  • Cross-Tenant Data Leak Test: Verify Tenant B cannot read or mutate Tenant A data under any condition.
  • RLS Superuser Prevention Gate: All application roles run under app_tenant_user.
  • Deterministic Cache Test: Tenant A and Tenant B never share cached HTML responses on wildcard domains.
  • Order Drain Test: Tenants in order_drain can fulfill existing orders while blocking new checkouts.
