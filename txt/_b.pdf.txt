1. Product Target
Build a multi-tenant commerce operating system with:
Public tenant storefronts
Private tenant dashboards
Platform administration
Configurable business capabilities
Retail, food ordering, services, bookings, quotes, and inquiries
Product, service, customer, order, inventory, payment, marketing, and analytics workflows
AI-assisted operations using approved tools and structured actions
Branded subdomains and verified custom domains
30-day trials with recurring billing
Real-time notifications and operational updates
Strong tenant isolation
Auditable, reversible, and observable business operations
Production-grade deployment, monitoring, backups, disaster recovery, and security controls
The system must be implemented as a stable shared runtime with versioned configuration and
modular capabilities. Tenants must not receive generated production code. The platform should
generate and manage validated business configurations, not arbitrary application code.
2. Non-Negotiable Production Standards
The platform is not production-ready unless all of the following are true:
Tenant isolation is enforced in application logic, database policies, storage, events, jobs,
exports, and AI tools.
All financial operations are idempotent and auditable.
[Page 2]
Payment status is derived from verified provider webhooks, not browser redirects.
Every important state transition is explicit, validated, logged, and recoverable.
Configuration changes support drafts, previews, publishing, version history, and rollback.
AI actions are constrained to approved tools and validated schemas.
Background jobs are retry-safe and tenant-aware.
Customer data can be exported and deleted according to policy.
Backups are encrypted and restore-tested.
Deployment is automated with approval gates for production.
Security testing includes automated and human review.
Operational incidents have runbooks and assigned ownership.
The system supports graceful degradation when third-party services fail.
All APIs return consistent errors, request IDs, and traceable audit information.
No critical or high-risk security findings remain unresolved before public launch.

7. Database and Tenant Isolation
7.1 PostgreSQL RLS
Enable RLS on every tenant-exposed table.
[Page 17]
Use a database session variable set by trusted server code:
select set_config(
  'app.current_organization_id',
  'organization-uuid',
  true
);
Policies must validate the session organization and active membership.
create policy organization_orders_select
on orders
for select
to authenticated
using (
  organization_id = current_setting(
    'app.current_organization_id',
    true
  )::uuid
);
For writes:
create policy organization_orders_insert
on orders
for insert
to authenticated
with check (
  organization_id = current_setting(
    'app.current_organization_id',
    true
  )::uuid
);
Do not rely exclusively on client-supplied tenant IDs.
7.2 Authorization Layers
Every protected operation must pass:
1. Session authentication

7.3 Database Rules
Tenant IDs cannot be updated.
Foreign keys must include tenant ownership where practical.
Use composite unique indexes such as (organization_id, slug).
Use database constraints for valid state values.
Use transactions for financial and inventory operations.
Avoid soft deletion without clear retention behavior.
Use immutable event tables for financial and audit history.
Add indexes for every high-volume tenant query.
Partition high-volume global event tables if required.

35. Final Release Gate
The final release should be blocked unless the following end-to-end scenario passes repeatedly in
staging and production-like environments:
User creates account
  -> Creates organization
  -> Selects business mode
  -> Configures brand
  -> Imports catalog
  -> Reviews imported records
  -> Publishes storefront
  -> Customer visits custom or platform domain
  -> Customer adds item or books service
  -> Customer completes checkout
  -> Payment provider confirms through webhook
[Page 64]
  -> Order or appointment becomes operational
  -> Tenant receives realtime dashboard update
  -> Staff fulfills or manages the transaction
  -> Customer receives confirmation
  -> Billing trial transitions correctly
  -> Renewal succeeds or fails safely
  -> Tenant can cancel
  -> Tenant can export data
  -> Tenant can request deletion
At every step, verify:
Correct tenant isolation
Correct permissions
Correct audit events
Correct notification behavior
Correct retries
Correct rollback behavior
Correct observability
Correct failure handling
36. Final Architecture Principle
The completed platform should consist of:
Stable shared runtime
+
Versioned tenant configuration
+
Approved modular capabilities
+
Strict multi-layer authorization
+
RLS-backed tenant isolation
+
Auditable AI actions
[Page 65]
+
Reliable billing state machine
+
Transactional commerce workflows
+
Tenant-scoped realtime events
+
Portable customer data
+
Observable background processing
+
Automated deployment and rollback
+
Tested disaster recovery
The ultimate production standard is not the number of templates, modules, or AI features. The
system is ready when:
A business can publish independently.
Customers can reliably purchase, book, or submit inquiries.
Owners can operate the business from the dashboard.
Staff permissions are correctly enforced.
Payments and billing reconcile predictably.
Failed jobs and provider outages recover safely.
Data can be exported and deleted.
Every important action is traceable.
No tenant can access another tenant’s data.
Production operations can detect, contain, and recover from incidents.
